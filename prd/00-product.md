# 00. プロダクト

本章はこのアプリが**何をするものか**を定める。目的・利用者の範囲・非目標・画面と操作・
機能の実装状況を集約する。技術構成は [01](./01-architecture.md)、認証は [02](./02-auth.md)、
データモデルは [03](./03-data-model.md) に委ねる。

## 目的

セキレイをモチーフにした**個人用**の Todo Web アプリである。GitHub アカウントでログインし、
自分のタスクを追加・編集・削除できる。作者の身の回りにセキレイが多いことがモチーフの由来で、
UI の中心にはセキレイのアイコンを置き、尻尾を振るアニメーションを付けている。

同時に、**「Next.js らしいデータのやり取り」を実際に動くアプリで確かめる場**という副次的な目的を持つ。
Server Component / Server Action と Hono API を組み合わせた構成そのものが題材であり、
機能の少なさは意図的なものである。この目的があるため、機能追加よりも
「構成をきれいに保つこと」「新しい API を試すこと」が優先されることがある。

## 利用者の範囲

**個人用**であり、利用者は作者本人 1 人を想定する。

- **共有・コラボレーションは設計に含めない。** タスクもプロジェクトも所有者 1 人に閉じており、
  他ユーザへの共有・権限付与・招待といった概念は持たない（[03](./03-data-model.md)）。
- サインインできるのは本人だけであるべきで、**GitHub の numeric id による許可リスト**で
  絞る方針を採る。⚠ **これは未実装である。** 現状は GitHub アカウントさえあれば誰でも
  サインインでき、サインインを拒否するフックも置いていない（[02](./02-auth.md)）。
  データはユーザごとに分離されているので他人のタスクは見えないが、
  「入れてしまう」こと自体が理想との gap である。

## 非目標

次は**やらない**と決めているものである（「まだやっていない」ではない）。

| 非目標 | 理由 |
|---|---|
| 利用者間でのタスク / プロジェクト共有 | 個人用に閉じる。データモデルも所有者 1 人を前提にしている |
| 通知・リマインダ（メール / プッシュ） | 個人用の一覧として使えれば足りる |
| モバイルアプリ化（ネイティブ / ストア配布） | レスポンシブな Web で足りる |

⚠ **オフライン対応は非目標ではない。** 初期構想には「localStorage と Client Component で
ある程度のオフライン使用に耐える」という項目があり、当面やらないだけの**長期の検討事項**として
扱う（[01](./01-architecture.md) §gap / 検討中）。

## 画面と操作

画面は **2 つだけ**である。

| パス | 役割 | 認証 |
|---|---|---|
| `/` | アプリの紹介とサインインボタン | 未ログイン向け |
| `/tasks` | タスク一覧と追加フォーム | ログイン必須 |

`nextjs/src/proxy.ts` がログイン状態で**強制的に振り分ける**。ログイン済みなら `/tasks` 以外を
叩いても `/tasks` へ、未ログインなら `/` へリダイレクトする。matcher はこの 2 パスのみで、
それ以外のパスは素通しである。⚠ この振り分けは cookie の**存在**しか見ておらず、
UX 上のリダイレクトに過ぎない。実際の防御は API 側にある（[02](./02-auth.md)）。

**ルートを紹介ページにしたのは OG image を取らせるため**である。以前はルートを認証必須にして
タスク一覧を出していたが、アプリの URL を貼って紹介する際にクローラが OG image を取得できなかった。
サービスの説明自体も欲しかったので、ルートを紹介ページに変えた。

### ヘッダ

全ページ共通のヘッダには `Welcome: <name>` の表示とサインアウトボタンだけを置く
（`nextjs/src/components/Header.tsx`）。ナビゲーションは無い（行き先が 2 つしかなく、
`proxy.ts` が状態で決めるため）。

**ダークモードに対応**している（`next-themes` を `enableSystem` / `attribute='class'` で使用）。
⚠ **切り替え UI は無く、OS の設定に追従するだけ**である。

### タスクの操作

`/tasks` でできる操作は次の 3 つだけである。

| 操作 | 実装 |
|---|---|
| 追加 | 画面下部の `TaskInput` フォームに本文を入れて送信 |
| 本文の編集 | 一覧の各行のテキスト入力を直接編集。**500ms の debounce で自動保存**（`TaskItem`） |
| 削除 | 行末のメニュー（`TaskItemMenu`）→ Delete task（`DeleteTaskButton`） |

- **保存ボタンは無い。** 編集は入力が止まってから 500ms 後に `updateTask` が走る。
- **完了のチェックボックスやトグルは無い。** 「完了 = 削除」を仕様として選んでいる（次節）。
- 一覧は `TaskList`（Server Component・`'use cache: private'`）が**一括で取得**して子に渡す。
  1 ユーザあたり高々 100 個程度を想定した設計で、ページングや仮想スクロールは持たない。

### タスクの完了

🔴 **「完了 = 削除」を仕様とする。** 終わったタスクはメニューから削除して一覧から消す。
チェックボックスやトグル、完了済みタスクのアーカイブ表示は**導入しない**。
シンプルな個人用を意識しているためである。

⚠ 結果として、DB の `Tasks.done` 列は**どこからも使われていない**。将来の削除候補として
[03](./03-data-model.md) に記録している。

### 既知の表示上の挙動

- **タスク追加の結果表示が常に同じ。** `TaskInput` は `useActionState` の返り値として
  固定文字列 `"task added!"` を返すため、**成否に関わらず必ず同じ表示**が出る。
  追加に失敗しても成功したように見える。
- **失敗が画面に出ない。** Server Action（`nextjs/src/actions/tasksActions.ts`）は
  失敗時に `console.error` を出して `undefined` / 空配列を返すだけで、画面には何も表示しない。
- **cookie が残ったままセッションが無効になると、`/tasks` に留まって空の一覧が出る。**
  `proxy.ts` は cookie の存在しか見ないので `/tasks` に通し、API は 401 を返し、
  一覧は空配列になる。サインイン導線も出ない。

いずれも「失敗を画面に出す」「401 はサインイン導線へ誘導する」というあるべき姿との gap である
（[01](./01-architecture.md) §gap / 検討中）。
